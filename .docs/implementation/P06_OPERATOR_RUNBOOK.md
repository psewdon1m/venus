# P06 — установка, обновление и восстановление Venus

Scope: standalone-local-pilot-v2, один host, loopback. Разработка P07 не начата. Решение о доверии: [ADR-031](../adr/ADR-031-p06-standalone-operator-boundary.md). До тестов закреплён [recovery profile](p06-recovery-profile.v1.json). Реальный `venus-v0.0.1`, защищённый signing key, опубликованные assets и production activation имеют отдельные фактические статусы в реестре; fixture PASS их не заменяет.

Исполнитель UID1001 с группой1002 и UI UID1002 отличаются от consumer UID1000. Файлы executor.json/trust.json устанавливаются администратором в `/etc/venus`, не принимаются через web. Production использует отдельный/rootless Venus Docker daemon и проверенные unit files; локальный Docker Desktop drill не доказывает production daemon isolation. Shared Nginx/certbot и другие проекты не устанавливаются и не меняются. Operator listen в контейнере публикуется только как127.0.0.1:4310; для host-service необходимо bind127.0.0.1. Consumer loopback4300, PostgreSQL без host port.

Обязательные поля executor.json: `project` (venus-<installation>), `local_root`, `host_root` (соответствующий host bind source), `port`, `app_origin` (canonical HTTPS loopback, например `https://127.0.0.1:4300`), `compose_template`, `trust_file`, `socket`. Operator config: `origin`=`http://127.0.0.1:4310`, `port`4310, `token_file`, `socket`. Корневой SPKI/key_id доверия доставляется независимо от скачанного релиза. Только сервисный trust key допускает service release; fixture anchor помечен fixture и ограничен отдельным loopback registry.

Первичная подготовка — явная root-команда `node tools/venus-operator/provision.mjs /var/lib/venus /secure/operator-input-file`. Она не запускается при restart/restore, не перезаписывает существующие ledgers/keyring. Operator key — точные байты явно выбранного файла: без trim, normalization, minimum strength/composition или denylist. Для HTTP используется обратимое base64url-кодирование UTF-8 bytes; значение не сохраняется в browser storage. Секреты не передаются аргументом: аргумент указывает файл, а не значение. Provision создаёт machine-generated DB password и keyring, отдельные protected и witness каталоги; backups — owner-only. `operator-credentials` монтируется directory read-only; замена `key` видна при следующем запросе. Для systemd имена пользователей/UID и rootless socket должны быть заранее проверены администратором; существующие чужие UID не переназначаются.

Порядок установки: прочитать точный signed manifest и независимый trust anchor; `node tools/venus-operator/cli.mjs import /etc/venus/executor.json /verified/release-directory`; затем `install /etc/venus/executor.json <release_id>`. Импортируется только три bounded immutable файла; install проверяет image config/OCI identity и source/version labels. Выполняется только установленный compose template, архивный YAML не исполняется. Повторная initial install не заменяет корректную установку. Образы/данные чужого project labels не обслуживаются.

Для обновления оператор входит в отдельную панель, выбирает проверенный release, создаёт job, отдельно подтверждает и применяет. Нет fields shell/path/URL/upload. Сохранённый job UUID и фазовый журнал переживают reload/502/перезапуск; UI показывает неподтверждённое действие как ошибку, не как success. Повторный apply не создаёт вторую мутацию. После interrupted job обязательна явная команда recover через панель/API либо `recover /etc/venus/executor.json <job_id>`; live lock нельзя «лечить» удалением файла.

Backup — один host-файл `backups/<job_id>.vbackup`, magic VENUSBK1, bounded manifest и PostgreSQL custom dump. Он создаётся только после quiesce app; временный файл не является успешной копией. Внешний механизм копирует файл самостоятельно, Venus не сообщает его успех. `.env`, credentials, keyring и защищённые ledgers в backup не входят. Для восстановления нужны отдельно сохранённые keyring и актуальные protected ledgers; DB-файл не является полной копией новой машины без этих зависимостей. Не удалять и не откатывать `protected`: global high-water и topic birth/chain/witness metadata должны быть новее либо равны восстановленной БД. Missing/corrupt/regressed authority блокирует serving.

Восстановление останавливает app и проверяет fresh backup/hash/schema/source до drop/create целевой БД. Затем pg_restore выполняется single-transaction, запускается совместимый A, выполняются boot/reconcile/retirement barriers и readiness. Только после успешной проверки открывается serving. Подмена image на schema-incompatible без backup restore запрещена. Offline previous image сохраняется до mutation. Исходный fault и отдельный rollback outcome доступны по job ID. При recovery-failed serving остаётся закрытым, файлы данных и журнал сохраняются для расследования.

Публикация: только qualified `venus-v0.0.1` на exact main SHA и один immutable OCI digest; не перепаковывать tag/assets. Общий CI не имеет release secrets. Реальный protected signing environment и внешняя проверка опубликованных assets обязательны до service-release PASS. Если ключ или публикация недоступны, реестр отражает внешний blocker, а не fixture success. Production domain venus.shmoza.net, Cloudflare/certbot/DNS/TLS/UDP не являются локально пройденными проверками.

Откат P06: закрыть serving, отозвать candidate для новых install, применить совместимый image/config/schema и проверенную копию; protected metadata сохранить. P05 SOURCE20/SOURCE22 не являются принятыми release rollback targets. Нельзя выполнять global docker prune/compose down без project identity; cleanup удаляет только явно созданные disposable fixture ресурсы.

Встроенный runtime profile называется `local-pilot`; standalone-local-pilot-v2 — scope приёмки, не подмена этого runtime enum. App HTTP loopback располагается за будущим локальным HTTPS ingress; настоящий ingress/DNS/TLS относится к P07/production, не заявляется P06 install health.
