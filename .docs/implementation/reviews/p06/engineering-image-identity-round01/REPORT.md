1. driver.mjs:36–38 pulls/inspects the signed immutable OCI reference, then requires image.Id===release.image.config_digest. A correctly signed service built with the actual config digest90cd... would be rejected on the evidenced Desktop store whose Id is0653678..., even though the exact OCI RepoDigest and labels match. This follows directly from the comparison; no service installation was run to assert a particular terminal job outcome.
2. driver.mjs:40–41 uses signed config_digest as an inspect/save/load local locator and also equates the offline receipt image_id to config_digest. driver.mjs:44 and48 inject config_digest as compose image. These operations depend on a config digest resolving as an engine-local image. The observed manifest-Id engine breaks that assumption; parent additionally reports config lookup absent. This can prevent clean install/start, previous-image cache preparation and offline recovery.
3. tools/p06_release_inputs.py:16,22,26 obtains the signed field config_digest from inspect.Id. On a classic-store runner that may happen to be the actual config digest; on the observed store it would sign the OCI manifest digest into a field intended to bind config identity. Using one engine-dependent field for both semantics is wrong in either direction.

## Minimal implementation proposal

Keep the signed contract's two stable identities: immutable repository@OCI digest and actual OCI config digest. Do not redefine config_digest as localId and do not simply accept Id equal to either digest. Docker inspect Id is only an engine-local locator; it is useful for local operations after independent identity verification, not as a portable config proof.

Release input preparation should derive the actual config digest from the exact built OCI manifest descriptor (build metadata already includes containerimage.config.digest for this single-image build), and check it against the pulled image's actual config bytes/descriptor. Retain exact source/version labels. A manifest/index must be distinguished explicitly; ambiguous or unsupported layouts fail closed rather than selecting an arbitrary entry/platform.

In the driver, inspect/pull the signed immutable OCI reference and retain exact RepoDigest matching. Verify actual config independently of Id: inspect a local docker image save archive without extracting/executing it. For OCI layout, verify the selected exact manifest blob hash against signed OCI digest, its config descriptor against signed config_digest and hash the corresponding config blob bytes; for Docker-save layout, verify the single selected config blob's bytes against signed config_digest while binding archive creation to the already verified exact RepoDigest. Validate source/version labels from the verified config as well as inspect data. Bound metadata/config sizes and archive traversal, reject duplicate/ambiguous metadata or unsafe paths; image layer bodies can be streamed/skipped rather than buffered/extracted. Existing small release-bundle parsing is not directly reusable with its16MiB whole-archive limit.

Use the immutable reference or the independently verified returned local Id for compose/start/save operations, never the signed config digest as a presumed local ID. For offline restore account for Docker-save layouts that may not restore a repository digest alias: save a deterministic project-owned local tag made from the verified image and restore it from the exact hashed archive, or persist and resolve a verified engine-local locator. Receipt must bind the signed OCI reference/digest, signed config digest, exact archive SHA256 and the owned local locator. After load, revalidate actual config bytes and source/version before start. Do not require a network pull or relax identity because an alias is absent; fall back only through the archive receipt created while exact OCI identity was verified. Receipt/local alias must never be treated as substitute signed identity or accept arbitrary repositories/arguments. No change to consumer credentials, DB, labels, privilege boundary, serving gate, backup/ledger semantics or manifest signature checks is needed.

Update the existing fixture's ID usage consistently, retaining its actual own-image removal, registry stop and offline archive load. Relevant bounded verification after the implementation should cover differing Id/config semantics and real offline recovery on the supported engines in the existing mechanism.
