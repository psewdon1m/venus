# Read-only V2 socket preparation public projection audit

Finding: the V2 socketView public `game` result is unused by every current repository consumer. Removing **only** its two await-this.view computations is a reasonable narrow application optimization, subject to root author tests/review; no edit is made here. Measured speedup is not established and the7s profile shows other private-preference/lifecycle ledger reads remain substantial.

Source scope is exact A11 source597f1a35/1860. `Rooms.socketState:392–411` returns `{room,game,privateEvents}`, with member/original credential fence before child work and fresh/final original credential fences afterward. `Rooms.liveGrant:360` consumes only `.room`. Production WebSocket auth/poll are the only other production consumers (`room-routes:185,197`), and `sendGame:163–168` reads only bundle.room and privateEvents. Initial/changed public delivery always invokes `Rooms.dispatchGame`, never bundle.game. `Rooms.dispatchGame:377–390` explicitly forbids enqueue of the cached preparation projection and performs a fresh room/member/acceptance/child publicDelivery/final authorization/publication capability check under its own room lock.

Search of apps/packages/tests/tools found no bundle.game consumer, including destructuring of socketState results at all enumerated callsites. P03 integration uses private references only; P05 topic wire fixture uses privateEvents only; P04 server aliases/wraps socketState solely to pause/return the original bundle. RoomGames routes the nullable hook result without inspecting its game field. Root normal server is the scope; unknown external consumers of the exported internal class are not claimed compatible.

`TopicGames.socketView:331` has exactly two public view result branches: a deferred private preparation return and the final return. Returning `{game:null,...}` at these locations keeps active loaded/current history/safety/source/presence checks, actor-specific prepareProjection, its exact failures/deferred behavior, old-recipient reference selection/order/max100, and all Room credential fences. Do not remove the active loaded branch, private prepare/refs, or final dispatches. Legacy `Games.socketView` remains unchanged; RoomGameHooks already permits game:null. No public HTTP/WS schema or serializer change is required.

Explicit behavior caveat: for inactive/waiting/paused games the old call to view could be the child's only content/history check in this preparation method. Skipping it delays detection of malformed/source content until fresh delivery is actually attempted; it does not authorize or publish that cached content. Source/publication checks still apply in dispatchGame/publicDelivery and privateDelivery. Known content outages already preserve room transport via RoomGames. This must be described as removal of redundant preparation validation, not a promise that every former error occurs at the same poll. If an external requirement demands eager inactive validation, this two-line change alone would not preserve that requirement; no such current wire contract/consumer was found.
