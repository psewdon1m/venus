## Loader and approval contract

Inputs are bounded UTF-8 raw bytes for map, taxonomy and semantic policy, a validated FrozenPack, and an **externally trusted approved pin record**, not an approval Boolean read from the supplied candidate. Compute and verify raw SHA256 before parsing; use duplicate-key-rejecting JSON parser, finite limits, exact fields for the normalized runtime schema and explicit revision dispatch. Bind canonical taxonomy/semantic hashes as well as exact approved raw hashes. Unknown revisions and unknown required fields fail closed.

Production loading requires: `pack.synthetic === false`; pack already reviewed by its existing loader; all three records explicitly approved/runtime eligible with required classification statuses and no HOLD or unresolved required editorial/localization flags; the trusted registry record matches all actual hashes and revisions; map pack digest equals the actual FrozenPack digest. Caller must separately prove the trusted pin record is current and unwithdrawn, including again at final delivery. A typed object cannot authenticate a registry by itself.

The test path must require a separately identifiable **synthetic-fixture capability** in addition to `pack.synthetic === true` and `SYNTHETIC_MACHINE_FIXTURE` map/taxonomy/family statuses. It must reject reviewed packs and normal candidate450 inputs. No `allowUnapproved: true` option and no environment-based override. Suggested capability: an opaque branded token minted by a distinctly named fixture factory, tracked by module-local WeakSet; never re-export that factory through the production package index. Runtime bundling/entry-point gate must independently verify the fixture entry is not called/imported in production. The token is an explicit test guard, not a security boundary against arbitrary code in the same process.

Every FrozenPack card has exactly one map entry matching ID/revision/canonical hash, actual mode/interaction and complete RU/EN/TR field commitments. Nonempty unique known topics are a union over all sides/locales; no runtime semantic inference. TD choices share the same union. Every family reference must exist, contain the exact card revision/hash/interaction, and reverse membership must match. No duplicate references, unknown topic/family, stale raw/canonical hash, missing side/locale, oversized list or extraneous reference. Entire mixed families are marked unavailable for all participants before any history filtering. Do not delete their cards from the original pack. Empty historical families remain lineage, not eligible candidates.

Raw candidate source paths and rationale remain authoring data; normalized runtime accessors return only exact pins, card/topic/family references and localized topic labels. No client serialization of loader objects or history. Newly approved classification hashes require a new trusted approval entry; do not mutate candidate02 flags in place.

## Versioned snapshot and history contract

Envelope: `schema: 2`, `engine_revision: RE-1.P05-TOPIC-1`, exact unchanged `baseline: SnapshotV1`, `private_policy_revision`, raw/canonical map/taxonomy/semantic pins and a repertoire digest incorporating unconditional exclusions. Validate baseline with the existing immutableSnapshot, preserving its canonical bytes. Validate a distinct exact schema2 field set. Never add a topic capability to schema1 capabilities.

Public room history and encrypted pair-private history are separate authenticated inputs with room ID, monotonically committed sequence/revision, exact originating session/round, card ID/revision/hash, mode, actor scope and policy/pack/map pins. Room/member lifetime and unique actor IDs are mandatory. Public entries must be actual publicly disclosed prompts. Private entries belong to the same unordered two-person scope in the same room, while the selected directed actor order is pinned per round. No private entry from another pair/room may constrain a new pair. Public history can constrain private candidates; private history cannot constrain public scheduling. Changing mode/session does not erase applicable history. A new room does. Foreign/downgraded/unknown map or history revisions fail closed until an explicit migration is implemented, rather than silently treating them as empty history.

Current-session RoundHistoryV2 records **actual** effective card references and every replacement/offer attempt with offer epoch, safety revision, candidate counter, exact old/new candidate identity, disposition and disclosure state. Replacement cannot change round ID/index, actor pair/order, stage, snapshot comfort/relationship/context or existing deadlines. Changed prompt/TD-side/YesBut condition must receive a fresh exact consent binding. Declined attempts remain in the private record; no fabricated past plans or silent reroll. Idempotent exact replay returns the same candidate; stale expected history/safety/epoch revision denies rather than recomputing under a newer request.

The caller must transact current history and own room preference revisions with selection, then commit the returned immutable state before another call. The pure module cannot authenticate history, guarantee fsync/restore safety or arbitrate concurrent SQL requests. Those are explicit integration responsibilities. Only current approved pins and the monotonic safety ledger make a persisted history admissible after restore.

## New scheduling algorithm and required policy distinction

1. Fix the public schedule/domain independently of private topic settings, exclusions, private chosen card IDs, private attempts, own safety revision, topic offer epoch and pair-private history. Use baseline seed + new algorithm revision + public round index + **public** room/session history and public repertoire pins only. Domain-separate random streams for public slot/option/card/role/primary and private option/candidate operations. The public sequence includes metadata/round IDs/primary roles, not just card ID.
2. Reserve private opportunities with the existing stage target rates (0/0/.22/.4) and hard ceiling `ceil(.25 * total_rounds)`, based on **scheduled generic opportunities**, not accepted/declined/filtered private prompts. Never silently replace a private opportunity with a public card when the topic pool is empty. Room view remains the same generic slot; recipients get a candidate offer or safe-empty. Cap counts must be explicit and finite; replacements stay inside their original opportunity and do not create more rounds/budget.
3. Public general/pair branching retains stage rates [.2,.4,.6,.6], all existing eligibility guards and common-support public repertoire. Preserve epsilon .05 relationship-prior branch and pair weights only where they already apply; do not derive public weights from private topic sets or histories. Public appearance/recovery metrics use public events only; private appearance/recovery metrics use appropriate actual private history and applicable public events. Anti-consecutive identical private pair and weighted inverse appearances remain within the private option domain where safe alternatives exist.
4. Private option eligibility keeps base class/comfort/stage/context/capabilities/consent guards and common baseline support requirements. Apply both actors' current explicit allow sets, both monotonic room exclusions and applicable public/pair-private semantic/card history before selecting a candidate. Any disallowed tag blocks the complete card. Default empty allow yields no private prompt. Unknown/missing owner state yields no candidate. A smaller valid pool must not relax filters or reveal exact counts or which person denied a topic.
5. Deterministic private stream binds baseline seed, exact current round/actors, offer epoch, candidate counter, map/repertoire pins and safety revision. Candidate scan is bounded by actual pack size; exclude previous card IDs and applicable family IDs including declined/replaced attempts. Selection never alters actor pair or stage to make a desired question fit. Changing topic/private history must not consume public RNG calls.
6. Actual effective card intensity participates in subsequent **private** recovery/fairness. Public soft recovery uses only previous publicly observable intensity. Applying hidden private intensity to public recovery would violate the new privacy invariant. This is a deliberate new versioned policy distinction, preserving the old policy's mechanism and probabilities in each visibility domain, **not a claim of identical legacy distributions**. New fairness/inference evidence and explicit ADR/contract wording are required before activation.
7. Safe-empty is a typed internal result, projected generically. Start preflight reports unsupported capacity separately from successful complete sessions and cannot weaken filters. Full public shortage fails before admission. Private all-excluded/semantic exhaustion stays a safe-empty private opportunity; whether a product session requires at least one playable private prompt is a caller/product criterion that must be explicit in the preflight report.

Potential policy point for root implementation: exact equality of public sequence under arbitrary private history requires the fixed opportunity schedule and public-only appearances/recovery above; preserving the legacy algorithm's global private-dependent scheduling and that equality is impossible. This is an engineering revision under the already authorized new schema2 design, not a new request to the human owner.

## Integration with the separate conversation kernel

The new planner supplies `ConversationScope`, exact pack/map/taxonomy pins, vocabulary and a server-private list/selected candidate binding. The kernel can then bind exact candidate to a fresh independent offer token; before bilateral accept no card ID, prompt hash, candidate-derived token, preview or length goes to the recipient. The planner's deterministic server-private candidate reference must not be used as the public offer token. Runtime creates unique unpredictable content-independent tokens.

Room preferences are supplied from an independently encrypted room-member ledger and retained across mode/session/pair changes. Kernel-local preferences do not themselves establish that room lifetime. Other-question/revoke first invalidates the old epoch/transcript/advice/queued delivery refs, persists any new room exclusion through safety ledger fsync and commits private attempt history, then invokes a new candidate selection or records safe-empty. All stale accepts remain invalid even when no alternative exists. Current approved catalogue/map, room/presence/membership/deletion, exact current round/pair, both preferences, epoch, TTL and selected reference must be checked synchronously before dispatch after awaited IO.

Schema2 transport must not use the older chat-v1 path as an escape hatch. New module export does not enable starts; root must wire feature flag default-off and version-dispatch-safe refusal first. Rollback stops new V2 starts, terminates/revokes existing V2 moments, keeps monotonic room exclusions, and preserves old snapshots/readers unchanged; unsupported restored V2 sessions terminate safely instead of becoming legacy sessions.
