# Production topic source — design checkpoint

2026-10-19, author `/root/p05_targeted_review`. No included writes yet.

## Release-only trust boundary

Add `approved-topic-bundles.json` with `{schema_version:1,approved:[]}`. No entries are added to either production registry. `topic-bundles.ts` imports this immutable release JSON and existing `bundledPacks`; its production export is a frozen array of `{pack,map,active}` records. A validating offline loader accepts registry data and the exact authorized reviewed pack set for tooling/tests, not HTTP/env/file paths. Each registry entry contains `{trusted,bytes:{map,taxonomy,semantic},active}` where all three byte strings use canonical base64. The trusted fields are the exact `TrustedTopicPins`; `FrozenTopicMap.load` verifies approval status, raw SHA256 hashes, every card/locale/semantic binding and non-synthetic pack status. Pack digest must resolve uniquely in the authorized reviewed set; synthetic/unavailable/duplicate exact pin tuples fail. No URLs, hot-loading, implicit map conversion or synthetic factory exports.

Historical topic bundles remain in the release registry for pinned games even after a newer mapping becomes active. Multiple historical maps for one pack are allowed; each tuple retains exact full pins. Exactly one entry per pack may be marked `active:true` for new games, avoiding ambiguous selection. Older entries use `active:false`; this flag changes only new-session map selection, never the meaning of stored pins. An active catalog pack without an active approved map returns null, not the first historical map or a candidate map. Duplicate active maps for a pack fail startup. Full topic pins distinguish historical revisions and hashes; no silent upgrade by pack digest alone.

## API provider

Add `ReleaseTopicGameSource` implementing the existing `TopicGameSource` interface, constructed with the actual `GameCatalog` and protected `RevocationLedger`; it reads only the frozen production bundle array by default. Production source membership is an exact verified tuple, never just a caller-supplied map or digest. `active(c)` awaits actual `catalog.active(c)`, resolves that actual reviewed pack into the release active-map entry, and runs a final synchronous source/ledger fence. `pinned(c,pins)` resolves the full historical tuple, awaits actual `catalog.assertPinned(c,pack.digest)`, and repeats the synchronous fence. Unknown/mutated pins, missing maps, synthetic/unverified records and withdrawn pack revisions deny. The caller must already hold the global shared catalog transaction lock across these calls and final enqueue; the provider does not open another transaction or take a nested lock.

`assertCurrent(pins)` resolves exact pins to release-owned verified pack/map, repeats `FrozenTopicMap.assertVerified` and full pin equality, then calls the same protected ledger's synchronous `read()`. Missing/corrupt/regressed ledger denies; any ledger entry matching any card ID **and revision** in that pack denies the whole pack, including map-excluded cards. A different revision does not withdraw this immutable pack. This checks the complete pack at final delivery, with no async gap after the ledger fence. Shared-catalog lock is still needed to synchronize DB state/activation/reconciliation; this synchronous method does not pretend to query DB consistency.

## Test boundary and unresolved compatibility

Both production registries stay empty. Tests may use explicitly labelled machine-only reviewed-format boundary fixtures, matching existing catalog/map boundary tests; they do not create real human approval records or modify production registries. Dependency seams, if needed for the positive adapter tests, must remain explicit test-only construction and separate from the production factory; no flag enabling synthetic data in the production source. Prefer module isolation/mocking release exports in tests over a public provider argument accepting arbitrary maps. Actual ledger tests use protected temporary files and exercise withdrawal-after-await, corruption, missing files, rollback floors, exact-revision matching, old pins and default-empty behavior.

The room lifecycle/preferences registry currently carries global taxonomy/policy pins. Supporting old game source pins does **not** establish that old and new room preference vocabularies can interoperate. This loader does not auto-upgrade room pins or translate topics. Root must select compatible source/room pins or deny preparation pending a separate explicit migration/compatibility design. Old bundles must be retained until all pinned sessions and applicable recovery/rollback windows have expired.

Author preflight is limited to these files, tests, type/lint checks and exact snapshots. Another agent must independently review the implementation. No P05/full C2/restore/production/content450 approval claim.
