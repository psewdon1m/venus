# P05: временный текстовый канал пары

Актуальное дополнение V2 от 2026-10-20: владелец принял [ADR-025](adr/ADR-025-p05-unified-private-text-chat.md) — один канал для online и in_person. Для новых V2 snapshots прежнее online-only ограничение ниже заменяется этой новой политикой; исходные ограничения V1 и сохранённые доказательства остаются историческими. Реализация и независимые Docker-гейты новой политики ещё требуются.

Компонент реализует [ADR-007](adr/ADR-007-private-online-chat.md) в standalone-профиле; это подготовка P05, а не приёмка P04/P05 и не разрешение использовать draft-каталог. Исходные контракты P00/P03 и immutable snapshots сохранены. Новый транспорт описан отдельно: [private-chat.v1.schema.json](contracts/private-chat.v1.schema.json), типы — `packages/contracts/src/private-chat.ts`.

`VENUS_PRIVATE_TEXT_CHAT` принимает только `true` / `false`; отсутствие означает `false`, опечатка блокирует startup. Новые online snapshots получают `private_text_chat` только при включённом backend; старые snapshots никогда не дополняются capability. В in_person capability не объявляется. Без capability зависимые карточки недопустимы существующим engine selection.

## Контракт и права

GET/POST `/api/v1/rooms/:roomId/game/:sessionId/round/:roundId/chat` привязаны к текущему раунду текущей сессии. Доступ имеют только два actor текущей `pair_private`, после двух invitation accepts; обычный host не получает никаких специальных прав. Общая публичная пара с отдельным quiet consent не становится приватным чатом. Чат допустим и во время ожидания action consent: invitation согласие позволяет разговаривать, но не разрешает само действие. Отказ или истечение action consent также закрывает доступ.

GET требует room session cookie и `X-CSRF-Token`; browser GET может не содержать Origin. Присутствующий Origin обязан точно совпасть с APP_ORIGIN; присутствующий `Sec-Fetch-Site` обязан быть `same-origin`. POST всегда требует точный Origin и CSRF. Query-параметры не разрешены. SameSite/HttpOnly/Secure cookie, отсутствие CORS и `no-store` остаются обязательными.

POST: `{request_id: UUID, text: string}`; ответ `{request_id,message_id,chat_rev,expires_at}`. Повтор с тем же request_id от того же actor возвращает исходную квитанцию; другой текст даёт `IDEMPOTENCY_CONFLICT`. GET: `{session_id,round_id,chat_rev,expires_at,messages:[{message_id,sender_member_id,text,sent_at,expires_at}]}`. Порядок сообщений — по chat_rev. Это отдельная ревизия: сообщения не изменяют game_rev / room_rev, не создают game outbox и не требуют expected_rev. Poll возвращает последние 32 сообщения; отсутствие старых сообщений является нормальным свойством ограниченного буфера.

Сообщение ограничено 1000 Unicode scalars и 4096 UTF-8 bytes; пустое/whitespace-only, malformed Unicode, управляющие и bidi-formatting символы запрещены. Формат — простой текст; UI обязан показывать его как text, не HTML. HTTP body ≤8192 bytes. Лимиты: 12 новых сообщений за минутное окно на actor, 128 за раунд. Идемпотентный повтор не расходует квоту. Максимум 1024 volatile grants одновременно; при исчерпании создание нового приватного раунда отклоняется `PRIVATE_CHAT_CAPACITY_UNAVAILABLE` и SQL-транзакция откатывается. Недоступный канал не выдаётся за успешное приглашение и не подменяется публичной доставкой. Повторная регистрация существующего grant не продлевает TTL.

## Хранение, expiry и dispatch fence

Отдельная schema generation `venus_chat_schema_migrations=1` создаёт три таблицы; generation game schema остаётся 1. `private_chat_messages` содержит AES-256-GCM ciphertext с 16 KiB padding и AAD room/session/round/message. `private_chat_requests` хранит keyed fingerprint и квитанцию без текста; `private_chat_scopes` — счётчики и expiry. Текст, его открытый hash, заголовки, тела и cookies не записываются в audit/log/outbox/общую idempotency table. Это шифрование на сервере, не E2EE: API и два адресата получают plaintext в памяти/ответе.

TTL ≤5 минут и никогда не позже конца invitation (текущий invitation TTL — 3 минуты после второго accept); grant также не переживает 5 минут с создания раунда. GET не продлевает срок. Access/room state/deletion ledger, current session/round, неизменяемая membership/capability, точная пара actors, slots, online presence, heartbeat/reservation/session expiry обоих, текущая версия entry acceptance и consent проверяются под тем же room/catalogue transaction fence, что и отзыв. Перед синхронным HTTP enqueue снова проверяются часы; сообщения, истёкшие во время awaited reads, фильтруются. Async Fastify onSend не отделяет отправку приватного текста от fence.

Decline/stop/finish/skip/pause/disconnect/removal/close/pack withdrawal удаляют volatile grant и SQL scope с cascade на transcript/receipts. Очистка собственных setup-настроек участника running game атомарно завершает эту игру как aborted, сохраняя исходный snapshot; прежний snapshot с более высоким comfort нельзя возобновить. Следующая игра получает новые настройки. Room maintenance физически удаляет истёкшие записи; отложенный maintenance не продлевает доступ. Откат транзакции после удаления volatile grant допускает лишний отказ, но не возвращает доступ.

## Restart, restore и откат

Текстовый канал сознательно не восстанавливается после перезапуска API: при startup `migrateChat()` проверяет schema hashes и удаляет scopes с cascade. Новый `Games` имеет пустой volatile grant map, даже если БД восстановили из старой копии; grant создаётся исключительно при создании нового online private раунда в текущем процессе. При отсутствии рабочего grant старый online private раунд останавливается обычной reconciliation: invitation/action consents закрываются, condition и transcript очищаются. Игровая сессия продолжает существовать по P03, immutable snapshot не переписывается; следующий раунд может получить новый grant. Перезапуск с capability flag=false также не продолжает прежний online private момент.

До commit такой reconciliation финальные HTTP/WS projections независимо блокируют invitation, prompt, action и condition: только отказ/`private_cleared`, без save/bump/queue в read-only dispatch. Проверка grant повторяется после awaited reads. Обычный frozen capability в snapshot не подменяет доступный канал. Отсутствие capability не создаёт online bypass даже в synthetic factory. In_person private раунды не требуют chat grant и не расходуют его capacity.

Старое приглашение не возвращает grant. Восстановление уже отозванных SQL scope, активной game row и round cipher во время того же процесса также не возвращает удалённый volatile grant. Ветка safety reconciliation определяет online/in_person по authenticated frozen snapshot cipher и AAD без обращения к catalogue ledger; его недоступность не отменяет stop/clear. Полная проверка pinned snapshot/pack остаётся обязательной для нормальной доставки приватного содержимого.

Для отката выключить новые admissions/game starts, безопасно завершить активные приватные раунды, установить capability flag=false и перезапустить API: transcript/grants удаляются, новые snapshots не имеют chat capability. Предыдущий образ игнорирует additive chat schema; перед его запуском текущим образом удалить ephemeral scopes. Прежние migration bytes не меняются; таблицы/новую migration не удалять автоматически и не понижать generation. Финальный rollback требует проверки совместимого UI/API/engine набора, его выполнение здесь не заявлено.

## Проверки и границы

Новые API unit suites проверяют exact input/Unicode, browser GET CSRF/Origin/Fetch Metadata, безусловный POST Origin, ciphertext/AAD, bounded storage counters, rate/volume/idempotency, host/cross-context/неполное согласие/expired membership и final clock fences. Реальный PostgreSQL/HTTP/browser lifecycle, параллельный отзыв, DB dump без plaintext и restart/restore должны быть доказаны отдельным Docker integration report перед компонентной приёмкой; unit PASS их не заменяет. Никаких claims о production, внешней TLS/DNS или реальных мобильных устройствах.


## Protocol2: сохранение политики чата при topic epochs

Для нового topic transport применяются те же ограничения контекста и квот: серверный `VENUS_PRIVATE_TEXT_CHAT` default false передаётся в `TopicGames`; capability нового snapshot существует только для online+enabled. In-person private prompts остаются допустимыми без текстового канала. Текущие flag, room context, immutable capability, actor/consent, epoch и final delivery fence проверяются при send/read, exact retry и повторной HTTP-выдаче квитанции. Включение flag не расширяет старый snapshot. При flag-off текущий online private момент останавливается reconciliation; final fence отказывает до этой записи. Новая попытка выбрать online private по старому frozen cap при выключенном flag отклоняется до создания раунда. Stop/Leave/Close сохраняют независимость от content source.

`TopicRoundData.chat_quota` — приватное поле существующего зашифрованного round cipher с AAD room/session/round: schema_version1, exact round_id, total, calendar minute, actor_counts и last_sent_at. Это не новая SQL migration; исторические migrations/snapshot bytes не меняются. Лимиты наследуются:12 новых сообщений на actor за календарную минуту `floor(now/60000)`,128 за весь раунд, последние32 сообщения текущего epoch. Идемпотентный повтор не меняет quota/transcript. OtherQuestion/смена темы очищает старый transcript, сохраняя round quota; sequence растёт при обрезке текущего epoch. Максимальный текстовый буфер32×4096 UTF-8 bytes. Chat-only запись не повышает room_rev/game_rev и не создаёт outbox. Missing/malformed quota старого активного раунда не обнуляется: отправка fail closed; startup bootGate отзывает старые private scopes, новый раунд создаёт новый budget.

TG-CHAT-001 независимо воспроизведён на прежнем frozen source1d4de7; текущие исправления — кандидат до fresh actual PG/HTTP и независимого повторного review. TG-CHAT-002 — lone surrogate text validation, найденный при source review исправления; malformed Unicode теперь отклоняется вместе с control/bidi. Старые component PASS не принимают новые байты. Полный browser/restore/rollback/P05 gate остаётся открыт.
