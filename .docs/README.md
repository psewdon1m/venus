# Venus · Documentation Orchestrator

**Тип:** точка входа и оркестратор проектной документации · **редакция:** 1.0.0 · **дата:** 2026-10-18 · **status:** design specification / implementation pending.

## 1. Зачем нужен этот документ

Этот файл организует документы в единую систему требований: кто владеет контрактом, какие документы читать для изменения функции, как вести изменения, какие проверки блокируют выпуск и как отличать утверждённую продуктовую цель от технического предложения, ещё не доказанного на VPS/устройствах. Здесь нет второй конкурирующей спецификации продукта: содержание разделено по владельцам ниже.

**Слова:** `MUST` = обязательное требование; `MUST NOT` = запрет; `SHOULD` = предпочтение с задокументированным мотивом отступления; `MAY` = опция. `[ACCEPTED]` = зафиксированное решение продукта; `[PROPOSED]` = текущий конкретный контракт для реализации до ADR; `[SPIKE]` = нельзя обещать без практического теста; `[FUTURE]` = сознательно отложено; `[BLOCKED]` = запрещено считать готовым. Числовые настройки — первоначальные предположения; их замена требует метрик и сохранения свойств безопасности.

## 3. Порядок чтения и готовность

- **Разработчик продукта:** 01 → 08 → 04 → 02 → 09 → 03 → 05 → 06 → 07.
- **Frontend:** 01 → 03 → 04 → 08 → 02; каждый экран обязательно проверяется на `ru`, `en`, `tr`.
- **Backend/RTC:** 02 → 08 → 09 → 06 → 05 → 07; запрет открывать новые порты без инфраструктурного решения.
- **Автор карточек / агент:** 08 → 09 → `card.schema.json` → образцы → `tools/validate_cards.py` и `tools/validate_card_batch.py`.
- **Release operator:** Part 04/05/12 snapshots → 05 → 06 → 07; только по immutable релизным файлам и подтверждённому статусу зависимости.

После профильных требований читать [поэтапный план реализации](10_IMPLEMENTATION_PLAN.md). Он сохраняет продуктовые G0–G5 и задаёт отдельные этапы исполнения P00–P11, правила перехода, учёт решений и процедуру возврата. При создании плана этапы имеют статус `NOT_STARTED`; прохождение локальных проверок документации не закрывает гейты реализации.

Подготовленный комплект P00: [реестры и контракты](implementation/README.md), [актуальный статус](implementation/status.md), [решения владельца](implementation/USER_DECISIONS.md), [ADR](adr/README.md). P00 находится на рассмотрении; решения с участием владельца и независимая приёмка явно отделены от локальных тестов.

## 4. Порядок авторитетов и конфликты

1. Закон, безопасность пользователей и запреты на обход защиты контента.
2. Центральные обязательные нормативные правила Exocortex: Part 00 и применимые Part 01–13. В этом архиве дословно приложены только **Part 04**, **Part 05**, **Part 12**, предоставленные автором; **отсутствие других частей не даёт права придумывать их содержание или ослаблять общие требования**. Перед production release оператор обязан зафиксировать версии/sha применимых центральных частей.
3. Зафиксированные пользователем продуктовые решения (`[ACCEPTED]` в 01 и профильных документах).
4. Утверждённые местные ADR с тестами и обратной совместимостью.
5. Архитектурные рекомендации `[PROPOSED]` настоящего пакета; они не переписывают 1–4.
6. Примеры, мокапы, референсы: иллюстрируют, но не определяют контракт.

При **материальном расхождении**: остановить затронутую реализацию/релиз, создать запись `DIV-YYYYMMDD-NN` с двумя источниками, версиями, impacted interfaces/risks, owner, предлагаемым разрешением, ссылками на тест и решением по правилам Part 00. Нельзя тихо изменить локальный Markdown или объявить старый документ альтернативным стандартом.

## 6. Технические baseline-решения (предлагаемые, не выдавать за внедрённые)

- TypeScript monorepo: React/Vite client, Fastify Node API, PostgreSQL, WebSocket authoritative events, LiveKit self-hosted SFU как **отдельная инфраструктурная зависимость**. Не смешивать независимые циклы выпуска.
- Один app deployment `venus` с отдельными внутренними модулями и таблицами; не создавать микросервис на каждую логическую функцию до измеренной потребности.
- OAuth и регистрация **не нужны для начальной гостевой комнаты**; host capability хранить отдельно от invitation token; подписанные короткоживущие room sessions и серверное правоприменение.
- Каталог музыки только из файлов с проверенными правами на необходимый способ использования; Spotify не использовать как фон игр/общую трансляцию.
- Документационный каталог содержит семплы, а не 100 production-карточек/режим; отсутствие 300 проверенных карточек = блокер публичной Games readiness.

## 8. Контрольные ворота качества и согласованности

- **Doc gate:** `python tools/check_docs.py`; все ссылки внутри проекта и вложенные референсы существуют; список документов полный.
- **Relationship policy gate:** `python tools/check_relationship_policy.py` — проверяет 36 числовых ячеек, hard-veto и прогрессию (не заменяет реальные engine tests).
- **Content gate:** `python tools/validate_cards.py .docs/examples/cards`; `python -m unittest discover -s tools -p 'test_*.py' -v` (negative regression checks); JSON Schema + semantics + stable IDs + 3 locale + placeholders. Проверки образцов **не** равны проверке целевого каталога.
- **Functional gate:** конечные автоматы комнаты, игр, приватных согласий, WebSocket reconnection, media states покрыты unit/integration/e2e.
- **Privacy gate:** ни один HTTP/WS event для неавторизованного игрока не содержит чужого relationship edge; персональные данные не появляются в диагностических логах/аналитике.
- **UI gate:** desktop/mobile, keyboard/reflow/zoom, no visible scrollbar, no clipped actions, readable RU/EN/TR, reduced motion.
- **Release gate:** центральный Part 12 полный machine report (`PASS` либо доказательный `N/A` для всех ID), проверенный digest, подпись, сохранившийся rollback и readiness по Part 04/05.

## 9. Как вести историю и выпускать документацию

- Любой change request: номер, affected docs, причина, статус (`proposed/accepted/rejected`), контракты, тесты, миграция, rollback, ссылки на issue/PR.
- Контент и изменения алгоритма не объединять в одну непрослеживаемую публикацию. У каждого есть версия/snapshot и совместимость.
- Breaking изменения API/card schema/room state — explicit schema version, миграция и тест со старым клиентом.
- Редактировать исходные Part 04/05/12 snapshots ЗАПРЕЩЕНО; новая центральная revision подключается отдельно с SHA и отчётом о расхождении.
- Приватные тестовые данные только синтетические; не собирать настоящие crush/negative edges в тестовые fixtures или артефакты CI.

## 10. Выходной критерий документационного комплекта

Этот пакет готов к передаче разработчику, если все девять спецификаций, корневой README, этот оркестратор, три source snapshots, изображения, schema, образцы и инструменты доступны по действительным путям; ссылки разрешаются; JSON-образцы валидны. Это **не** означает product-release ready и не отменяет таблицу незакрытых ADR.
