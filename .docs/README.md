### Phase 1: Препродакшн (до начала проекта)

Эти документы описывают философию, правила и базовую архитектуру проекта. Их нужно изучить **перед началом любой работы**.

#### 1.1. [`README.md`](../README.md) — обзор проекта
**Что внутри:** Обзор проекта, архитектура, порядок чтения документации.  
**Зачем читать:** Общее понимание что такое Venus и как начать работу.

#### 1.2. [`constitution.md`](constitution.md) — корневые правила
**Что внутри:** Обязательные правила работы с проектом, coding standards, ограничения.  
**Зачем читать:** Понять КАК работать с проектом (языки, форматирование, запреты).  
**Критично для:** Всех участников и ИИ-ассистентов.

#### 1.3. [`git_managment.md`](git_managment.md) — git workflow
**Что внутри:** Branching strategy, версионирование, commit guidelines, release process.  
**Зачем читать:** Понять как управлять версиями и делать commits.  
**Критично для:** Любых git операций.

#### 1.4. [`manifest.md`](manifest.md) — философия и архитектура
**Что внутри:** Определение проекта, проблемы, сущности, принципы, сравнение с конкурентами.  
**Зачем читать:** Понять ЧТО мы строим и ПОЧЕМУ именно так.  
**Критично для:** Архитектурных решений и новых фич.

### Phase 2: Продакшн (во время разработки)

Эти документы создаются и используются во время активной разработки. Они направляют процесс реализации.

#### 2.1. [`stack.md`](stack.md) — технологический стек
**Что внутри:** Все технологии проекта и 15+ готовых решений для интеграции.
**Зачем читать:** Понять ЧЕМ строить и что можно делегировать готовым решениям.
**Критично для:** Технических решений и выбора инструментов.

#### 2.2. [`stages.md`](stages.md) — этапы разработки
**Что внутри:** Пошаговый roadmap с техническими деталями, контрольные точки КТ1-4.  
**Зачем читать:** Понять КОГДА и ЧТО реализовывать, в каком порядке.  
**Критично для:** Planning и implementation.

#### 2.3. [`traceability_matrix.md`](traceability_matrix.md) — трассировка требований
**Что внутри:** Связь требований манифеста с этапами реализации, статусы, прогресс.
**Зачем читать:** Понять какие требования покрыты и что осталось сделать.
**Критично для:** Sprint planning и reporting.

#### 2.4. [`directories_tree.md`](directories_tree.md) — структура проекта
**Что внутри:** Полная структура директорий и файлов.
**Зачем читать:** Понять ГДЕ находится код для каждой части системы.
**Критично для:** Навигации по проекту.

#### 2.5. [`ci-cd_pipeline.md`](ci-cd_pipeline.md) — автоматизация
**Что внутри:** CI/CD процессы, deployment strategy, rollback procedures.  
**Зачем читать:** Понять как код попадает в production.  
**Критично для:** Deployment и DevOps.

#### 2.6. [`secrets_management.md`](secrets_management.md) — управление секретами
**Что внутри:** Стратегии управления секретами, ротация, безопасность.
**Зачем читать:** Понять как безопасно работать с sensitive data.
**Критично для:** Production deployment и security.

#### 2.7. [`cloud_setup.md`](cloud_setup.md) — настройка облачной инфраструктуры
**Что внутри:** Настройка доменов, SSL, серверов, deployment.
**Зачем читать:** Понять как развернуть проект в облаке.
**Критично для:** Production deployment и DevOps.

### Phase 3: Постпродакшн (после MVP)

Эти документы заполняются по мере развития проекта и отражают текущее состояние.

#### 3.1. [`passport.md`](passport.md) — текущее состояние
**Что внутри:** Текущий статус проекта, достигнутые milestones, active development.
**Зачем читать:** Понять ГДЕ мы сейчас находимся в разработке.
**Обновляется:** После каждого milestone и основных изменений.

#### 3.2. [`versions.md`](versions.md) — история версий
**Что внутри:** Хронология всех релизов с краткими описаниями.  
**Зачем читать:** Понять историю развития проекта.  
**Обновляется:** При каждом push с новым git tag.  
** ВАЖНО:** Редактируется только при реальном push, не вручную.

#### 3.3. [`api_usage.md`](api_usage.md) — примеры использования API
**Что внутри:** Практические примеры работы с Venus API.  
**Зачем читать:** Понять как использовать API в реальных сценариях.  
**Обновляется:** При добавлении/изменении API endpoints.

##  Критические правила чтения

### Для всех участников

1. **Последовательность обязательна:**  
   Phase 1 → Phase 2 → Phase 3 → Исходный код

2. **Все файлы Phase 1 критичны:**  
   Нельзя пропустить [`constitution.md`](constitution.md) или [`manifest.md`](manifest.md)

3. **Проверка понимания:**  
   После чтения Phase 1 вы должны понимать:
   - Какие языки где использовать
   - Как делать commits
   - Что такое Персона, Проект-альбом, Плейсхолдер
   - Почему Venus отличается от Behance/Dribbble

4. **Только потом код:**  
   После Phase 1+2 можно открывать `frontend/`, `services/`, etc.

---

### Для ИИ-ассистентов

**ИИ-ассистент ОБЯЗАН:**

1. **Прочитать все файлы Phase 1 перед любой работой**
2. **Явно подтвердить** прочтение каждого ключевого документа
3. **Следовать правилам из [`constitution.md`](constitution.md):**
   - Код на английском
   - Общение на русском
   - Нет эмодзи в коде
   - Контекстуальная разработка
4. **Соблюдать git workflow из [`git_managment.md`](git_managment.md):**
   - НЕ делать `git push` без разрешения
   - НЕ редактировать [`versions.md`](versions.md) без real push
   - НЕ редактировать [`constitution.md`](constitution.md) и [`git_managment.md`](git_managment.md)

## Как работать с документацией

### Добавление новой документации
1. Создайте файл в `.docs/` с соответствующим названием
2. Добавьте ссылку в этот README.md в соответствующую Phase
3. Обновите "Связанные документы" в конце каждого файла
4. Зарегистрируйте в [`traceability_matrix.md`](traceability-matrix.md)

### Обновление существующей документации
1. Следуйте правилам из [`constitution.md`](constitution.md)
2. Обновляйте даты последнего изменения
3. Поддерживайте актуальность ссылок

### Code review для документации
- Проверяйте орфографию и грамматику
- Убедитесь в актуальности информации
- Проверьте корректность ссылок
- Оцените полноту покрытия темы
